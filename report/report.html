Abstract

Job seekers routinely tailor their applications to every posting: they compare their resume against the requirements, work out which skills they are missing, prepare for likely interview questions and write a cover letter. Existing tools either match keywords mechanically, as Applicant Tracking Systems do, or rely on a single chatbot prompt whose output is generic and prone to hallucination. This project presents Job Hunter, a multi-agent career copilot built with LangChain and LangGraph that runs entirely on a local Large Language Model (Llama 3.2, 3B parameters) served by Ollama.

Seven specialised agents cooperate through a LangGraph state graph. These are a Resume Parser, Job Analyst, Match Scorer, Gap Coach, Interview Coach, Cover Letter Writer and Letter Critic. Independent agents run in parallel, and the writer and critic form a feedback loop that revises the cover letter until it passes a rubric or reaches a revision limit. Every agent produces typed output validated against Pydantic schemas. To make a small local model dependable, the system combines LLM reasoning with deterministic components: a skill matcher that understands aliases, skill families, alternatives and compound requirements; a hybrid fit score in which the LLM contributes only 30%; a rubric-based critic whose score is computed in code; and a hallucination guardrail that rejects any figure, placeholder or skill claim in the letter that cannot be traced to the resume.

The application provides a Streamlit interface with a live view of the agent pipeline. On the sample data, the hybrid matcher classified 12 of 12 hand-labelled requirements correctly, against 7 of 12 for naive keyword matching. The guardrail caught invented metrics and placeholder employers that the language model produced. All 20 automated tests and every system test case passed. A complete analysis takes about two to three minutes on an 8 GB Apple M1 laptop, with no data leaving the machine.

Chapter 1

Introduction

1.1 The Problem

Applying for a job well takes considerable effort. For each posting, a candidate must read the description, identify the must-have and nice-to-have skills, compare them honestly with their own experience, decide whether the role is worth applying for, prepare for the interview and write a cover letter that is specific to the company. Doing this for dozens of applications is tiring, so candidates often send generic applications, which recruiters tend to ignore.

Generative AI can help, but a single prompt to a chatbot (“here is my resume and a job description, write a cover letter”) has well-known weaknesses. The output is generic. The model may claim skills the candidate does not have, or invent impressive-sounding numbers. And there is no structured analysis of why the candidate fits or does not fit. Cloud chatbots also require the user to upload a resume, a document full of personal information, to a third-party service.

This project addresses these problems by decomposing the task into a team of specialised AI agents, orchestrated with LangGraph, running on a local language model through Ollama, and backed by deterministic checks wherever correctness matters.

1.2 Objectives

The main objective is to build a reliable, privacy-preserving multi-agent application that analyses a candidate’s fit for a job and produces actionable, honest application material. The specific objectives are:

  1. To design a multi-agent workflow in LangGraph with parallel execution and a self-correcting feedback loop.
  2. To use LangChain prompt templates and structured output (Pydantic schemas) so that every agent returns validated, typed data.
  3. To run the Llama 3.2 language model locally through Ollama so that resumes never leave the user’s machine.
  4. To compute an explainable fit score that combines deterministic skill matching with the LLM’s qualitative judgement.
  5. To generate a personalised learning plan for missing skills and a set of likely interview questions.
  6. To generate a tailored cover letter and automatically detect and correct hallucinated claims.
  7. To build an interactive Streamlit interface that shows the agents working in real time.
  8. To verify the system with automated unit tests, system test cases and a quantitative comparison against a baseline.

1.3 Real-World Applications

  1. Job seekers and students: quickly judge whether a role is a realistic target and tailor each application.
  2. College placement cells: help students prepare for campus drives by highlighting gaps against each company’s requirements.
  3. Career coaches and mentors: produce a structured starting point (fit report, gaps, interview questions) for coaching sessions.
  4. Upskilling platforms: recommend targeted mini-projects based on the skills a learner is missing for a target role.
  5. Recruiters: the same pipeline, run in reverse, can pre-screen candidates with an explainable score instead of opaque keyword filters.
  6. Privacy-sensitive settings: because inference is local, the approach suits organisations that cannot send personal data to cloud AI services.

Chapter 2

Problem Statement and Proposed Solution

2.1 Problem Statement

Given a candidate’s resume and a job description, the system must (i) extract structured information from both documents, (ii) determine which required and preferred skills the candidate has, (iii) produce an explainable fit score, (iv) recommend concrete steps to close skill gaps, (v) predict likely interview questions, and (vi) write a tailored cover letter that contains only facts supported by the resume. The system must run on a typical student laptop without paid APIs, keep personal data local, and remain reliable even though small local language models are prone to formatting errors, inconsistency and hallucination.

2.2 Existing Systems

2.2.1 Applicant Tracking Systems and Keyword Matchers

Many job portals and Applicant Tracking Systems (ATS) score resumes by matching keywords from the job description.

Limitations:

  • Exact keyword matching misses synonyms and related skills (e.g. “k8s” vs. “Kubernetes”, or FAISS as a vector database).
  • Compound requirements (“RAG and vector databases”) and alternatives (“LangChain or LangGraph”) are handled poorly.
  • They give a score but no explanation, learning guidance or application material.

2.2.2 Single-Prompt AI Chatbots

General-purpose chatbots can write cover letters and give career advice from a single prompt.

Limitations:

  • Output is often generic and not grounded in the candidate’s actual achievements.
  • The model may invent metrics, employers or skills (hallucination), and nothing checks this.
  • No structured, reproducible analysis: asking twice may give two different verdicts.
  • Resumes containing personal data are sent to an external cloud service.

2.2.3 Resume Builders and Templates

Template-based tools help format resumes and letters but do not analyse a specific job posting.

Limitations:

  • They do not reason about fit, gaps or interview preparation.
  • Personalisation depends entirely on the user’s own effort.

2.3 Proposed Solution

The proposed system, Job Hunter, is a multi-agent application in which each agent has one clearly defined responsibility. Agents communicate through a shared, typed state managed by a LangGraph StateGraph:

  1. Resume Parser: converts the resume into a structured CandidateProfile (skills, experience, quantified achievements).
  2. Job Analyst: converts the posting into JobRequirements, separating must-have from nice-to-have skills.
  3. Match Scorer: runs a deterministic skill matcher and asks the LLM for a qualitative judgement, then combines both into a hybrid score.
  4. Gap Coach: turns each missing skill into a short, concrete portfolio mini-project.
  5. Interview Coach: predicts six likely questions, including “gap-probe” questions aimed at weak areas.
  6. Cover Letter Writer: drafts a tailored letter using only real achievements.
  7. Letter Critic: reviews the letter with a five-point rubric plus code-based checks, and sends it back for revision if needed.

The Resume Parser and Job Analyst run in parallel, as do the Gap Coach, Interview Coach and Cover Letter Writer. The writer and critic form a loop that ends when the letter passes or the revision limit is reached, after which the best-scoring draft is selected. A Streamlit web interface shows each agent’s status live and presents the results in tabs.

2.4 Advantages of the Proposed System

  1. Privacy: the model runs locally through Ollama, so the resume never leaves the computer.
  2. No paid API: the system uses a free, open-weight model.
  3. Explainable scoring: the score is broken down into must-have coverage, nice-to-have coverage and experience fit.
  4. Hallucination resistance: a deterministic guardrail rejects unsupported figures, placeholder names and false skill claims.
  5. Self-correction: the critic–writer loop revises weak letters automatically, and the best draft is kept.
  6. Robust to small-model errors: structured output, output-length caps, timeouts and fallbacks keep the pipeline running.
  7. Actionable output: a learning plan and interview preparation, not just a score.
  8. Modular and testable: each agent is a separate function; the full graph is tested with a scripted fake model.

Generated content can still be imperfect. Users should review the cover letter and advice before using them.

Chapter 3

Related Work and Technology Review

3.1 Introduction

Conversational AI has evolved from rule-based programs to large language models that can follow instructions, reason over text and call tools. A newer trend is agentic AI. Here, instead of one model answering in one step, several LLM-powered components each take a role, share state and iterate. This chapter reviews the technologies this project builds on and explains how each is used.

3.2 Generative Artificial Intelligence

Generative AI refers to models that produce new content (text, images, audio or code) based on patterns learned during training. Text generators take a prompt and produce a continuation. In this project, generative AI is used in two ways: to extract structured information from unstructured documents (resumes and job posts) and to generate new text (learning plans, interview questions and cover letters). Generative models can produce fluent but false statements, which is why this project pairs generation with verification.

3.3 Large Language Models

Large Language Models (LLMs) are transformer-based neural networks trained on very large text corpora to predict the next token. Through instruction tuning they learn to follow natural-language instructions. Their behaviour is shaped by the prompt and by decoding settings such as temperature: low temperature gives more deterministic output (used here for extraction and scoring), while higher temperature gives more varied output (used for writing). Smaller models (1–8 billion parameters) can run on laptops but are less reliable at following complex formats. This motivates the structured output, validation and fallback techniques used in this project.

3.4 LangChain

LangChain is a framework for building applications powered by language models. This project uses several of its core abstractions:

  • ChatPromptTemplate: reusable system and human message templates with variables.
  • LangChain Expression Language (LCEL): components are composed with the pipe operator, e.g. prompt | llm | StrOutputParser().
  • Structured output: llm.with_structured_output(PydanticModel) sends a JSON schema to the model and parses the reply into a validated Python object.
  • Fallbacks: chain.with_fallbacks([...]) automatically retries with an alternative chain if the primary one fails.
from langchain_ollama import ChatOllama
from langchain_core.prompts import ChatPromptTemplate

llm = ChatOllama(model="llama3.2", temperature=0)
prompt = ChatPromptTemplate.from_messages([
    ("system", "Extract a structured profile from the resume."),
    ("human", "RESUME:\n{resume_text}"),
])
chain = prompt | llm.with_structured_output(CandidateProfile)
profile = chain.invoke({"resume_text": text})   # -> CandidateProfile object

3.5 LangGraph and Multi-Agent Systems

LangGraph is a library from the LangChain ecosystem for building stateful, multi-step agent workflows as graphs. A StateGraph is defined by a typed state, a set of nodes (functions that read the state and return updates) and edges that decide which node runs next. Key features used in this project are:

  • Parallel fan-out and join: several edges leaving a node run their targets concurrently; an edge from a list of nodes waits for all of them.
  • Conditional edges: a routing function decides the next node, which enables loops such as critic → writer → critic.
  • Reducers: state fields annotated with operator.add accumulate values from parallel branches instead of overwriting them.
  • Streaming: graph.stream() emits events as each node starts and finishes, which powers the live UI.

Multi-agent systems split a complex task among specialised agents. Compared with a single prompt, this gives each agent a focused prompt and schema, allows independent steps to run in parallel, and enables patterns such as generator–critic (reflection), where one agent reviews and improves another’s output.

3.6 Ollama

Ollama is a runtime for running open-weight language models locally. It downloads quantised models, serves them through a local HTTP API (port 11434) and supports JSON-schema-constrained output, which LangChain’s structured output uses. In this project Ollama runs Llama 3.2 on the user’s laptop, so no API key or internet connection is needed after the model is downloaded, and resume data stays on the machine.

3.7 Llama 3.2

Llama 3.2 is a family of open-weight models released by Meta. The 3-billion-parameter instruction-tuned variant (llama3.2 in Ollama, about 2 GB quantised) is used here because it runs comfortably on an 8 GB laptop at about 20–25 tokens per second. The model name is configurable, so larger models such as Llama 3.1 8B or Qwen 2.5 can be swapped in without code changes.

3.8 Structured Output with Pydantic

Pydantic is a Python data-validation library. Each agent’s output is described by a Pydantic model whose field descriptions double as instructions to the LLM. LangChain converts the model into a JSON schema, Ollama constrains generation to that schema, and Pydantic validates the result. Downstream agents therefore receive typed objects (e.g. profile.skills: list[str]) rather than free text that must be parsed.

3.9 Streamlit

Streamlit is a Python framework for building interactive web applications without separate HTML or JavaScript code. The project uses st.file_uploader for PDF resumes, st.text_area for inputs, st.status for the live agent log, st.tabs for results, st.plotly_chart for the score gauge, st.download_button for the cover letter and st.session_state to keep results across reruns.

3.10 Python

Python is the implementation language for the whole project: agents, graph, scoring, guardrails, user interface and tests. Its ecosystem (LangChain, LangGraph, Pydantic, Streamlit, pytest) makes it the de facto language for LLM application development.

Chapter 4

Architecture and System Design

4.1 System Architecture

The system follows a layered architecture (Figure 4.1). The presentation layer is the Streamlit web app (or the command-line runner). The orchestration layer is the LangGraph state graph that schedules the seven agents. The agent layer contains LangChain chains: prompt templates, the chat model and output parsers. The reliability layer contains deterministic Python components: the skill matcher, hybrid scorer and guardrails. The model layer is Ollama serving Llama 3.2 locally.

4.2 Agent Workflow (LangGraph)

Figure 4.2 shows the agent graph. Execution starts with two agents in parallel. The match node waits for both, then fans out to three agents. The writer and critic loop until the letter passes or the revision limit is reached, and then the best draft is selected.

The workflow steps are:

  1. The user provides a resume (PDF upload or pasted text) and a job description, then clicks Run the agents.
  2. The input is validated: the button is disabled for empty input, and very short input produces a warning.
  3. The Resume Parser and Job Analyst run in parallel and write profile and job to the state.
  4. The Match Scorer runs the deterministic matcher, asks the LLM for an experience judgement and computes the hybrid score.
  5. The Gap Coach, Interview Coach and Cover Letter Writer run in parallel.
  6. The Letter Critic scores each draft. If the score is below 8/10 and revisions remain, the draft goes back to the writer with specific feedback.
  7. Once accepted (or out of revisions), the highest-scoring draft is selected and all results are shown in the interface.

4.3 Module Description

4.3.1 User Interface Module (app.py)

Accepts a PDF/TXT resume or pasted text and the job description, checks the Ollama connection, lets the user set the maximum number of letter revisions, loads sample data, streams agent progress live and presents results in five tabs: Fit report, Learning plan, Interview prep, Cover letter (with revision history) and Agent trace.

4.3.2 Document Processing Module (documents.py)

Extracts text from uploaded PDFs with pypdf (or decodes text files) and normalises bullets and whitespace.

4.3.3 Agent Module (agents.py, prompts.py, schemas.py)

Defines the seven agents. Each is a LangChain chain (prompt | model.with_structured_output(Schema)) wrapped in a node function that reads from and writes to the graph state and appends a human-readable trace message.

4.3.4 Orchestration Module (graph.py)

Builds and compiles the LangGraph StateGraph: nodes, parallel edges, the join, the conditional revise/accept edge and the append-only reducers for drafts, critiques and the trace.

4.3.5 Scoring Module (scoring.py)

Normalises skills, expands compound requirements, matches skills using aliases, families, alternatives and resume-text search, and computes the hybrid fit score and its band.

4.3.6 Guardrail Module (guardrails.py)

Detects unsupported numbers, placeholder organisations and brackets, clichés and false claims about missing skills, and cleans prompt artifacts from generated letters.

4.3.7 Model Execution Module (Ollama)

Ollama serves Llama 3.2 locally. Each ChatOllama client sets a temperature, an output cap (num_predict = 1200) and a request timeout. A fallback chain retries at a different temperature if structured parsing fails.

4.5 Hybrid Fit-Scoring Algorithm

A score produced entirely by an LLM is unstable and can be inflated by hallucination. Job Hunter therefore computes skill coverage in code and lets the LLM contribute only a bounded qualitative component:

Fit = 0.55 × Crequired + 0.15 × Cpreferred + 0.30 × ELLM

where Crequired and Cpreferred are the percentages of must-have and nice-to-have skills matched, and ELLM ∈ [0, 100] is the model’s experience-fit judgement (clamped, and rescaled if the model answers on a 0–10 scale). Scores of 80 or more are a Strong match, 60–79 a Good match, 40–59 a Stretch role and below 40 a Weak match. A requirement counts as matched by the following steps:

  1. Expansion: “RAG and vector databases” becomes two requirements; items such as “1+ years of experience” and generic disciplines (“Software Engineering”) are removed, since experience is judged separately.
  2. Normalisation: lower-casing, removing filler words (“strong”, “experience with”) and mapping aliases (k8s → kubernetes, postgres → postgresql, RAG → retrieval augmented generation).
  3. Alternatives: “LangChain or LangGraph” matches if any option matches.
  4. Skill families: a category is satisfied by any member, e.g. FAISS/Pinecone/Chroma count as a vector database.
  5. Fuzzy and resume-text fallback: whole-word containment, a similarity ratio of 0.88 or more, or a whole-word search of the raw resume (in case the extractor missed a skill).

4.6 Guardrails and Self-Correction

The Letter Critic combines an LLM rubric with code-based checks (Table 4.2). The model answers five true/false questions and the score is computed as 2 points per passed check. Checks that can be done reliably in code override the model’s answer.

Because a revision can be worse than its predecessor, the system keeps every draft and selects the one with the highest score, breaking ties in favour of fewer fact-check flags and then the later draft.

5.3.2 Building Agents with LangChain

def default_llm_factory(temperature):
    return ChatOllama(model=config.MODEL_NAME, temperature=temperature,
                      num_predict=config.MAX_OUTPUT_TOKENS,          # stop runaway generations
                      client_kwargs={"timeout": config.REQUEST_TIMEOUT_S})

def structured(prompt, llm, schema):
    primary = prompt | llm.with_structured_output(schema)
    # retry once at a different temperature if parsing/validation fails
    return primary.with_fallbacks([prompt | retry.with_structured_output(schema)])

self.resume_chain = structured(prompts.RESUME_PARSER, extract, CandidateProfile)
self.job_chain    = structured(prompts.JOB_ANALYST, extract, JobRequirements)
self.letter_chain = prompts.LETTER_WRITER | write | StrOutputParser()

5.3.3 LangGraph Orchestration

class JobHunterState(TypedDict, total=False):
    resume_text: str
    job_text: str
    profile: Any
    ...
    drafts: Annotated[list, operator.add]      # append-only: parallel-safe
    critiques: Annotated[list, operator.add]
    trace: Annotated[list, operator.add]

g = StateGraph(JobHunterState)
g.add_edge(START, "parse_resume")
g.add_edge(START, "analyze_job")                         # parallel
g.add_edge(["parse_resume", "analyze_job"], "match")     # join
for node in ("gap_coach", "interview_coach", "write_letter"):
    g.add_edge("match", node)                            # parallel fan-out
g.add_edge("write_letter", "critique_letter")
g.add_conditional_edges("critique_letter", should_revise,
                        {"revise": "write_letter", "accept": "select_best"})

def should_revise(state):
    if state["critique"].score >= 8 or state["revisions"] > config.MAX_LETTER_REVISIONS:
        return "accept"
    return "revise"

5.3.4 Skill Matching and Hybrid Score

def skill_in(skill, candidate_skills, resume_text=""):
    terms = _terms(skill)              # alternatives + aliases + family members
    have = [normalize(c) for c in candidate_skills]
    if any(_similar(t, c) for t in terms for c in have):
        return True
    text = resume_text.lower()         # fallback: search the raw resume
    return any(re.search(rf"(?<![a-z0-9]){re.escape(t)}(?![a-z0-9])", text) for t in terms)

def fit_score(match, experience_fit):
    experience_fit = max(0, min(100, experience_fit))
    return round(0.55 * match.required_coverage * 100
                 + 0.15 * match.preferred_coverage * 100
                 + 0.30 * experience_fit)

def unsupported_claims(letter, *sources):
    known = set().union(*(_numbers(s) for s in sources))
    issues = []
    for m in NUMBER.finditer(letter):
        if m.group(1).replace(",", "") not in known:
            issues.append(f"The figure '{m.group(0)}' does not appear in the resume ...")
    for m in PLACEHOLDER_ORG.finditer(letter):          # XYZ, ABC, Acme ...
        issues.append(f"'{m.group(0)}' is an invented placeholder organisation ...")
    return issues

6.1 Testing

Testing was carried out at three levels:

  1. Unit tests for the deterministic components: normalisation, requirement expansion, alternatives, skill families, resume-text fallback, false-positive prevention, score weights, and each guardrail.
  2. Graph tests that run the complete LangGraph workflow with a scripted fake chat model. They verify the parallel branches, the revision loop and its limit, best-draft selection, and that code checks override a lenient critic. Because no real model is needed, they run in under one second.
  3. System tests of the running application with the real Llama 3.2 model, plus headless UI checks using Streamlit’s AppTest and a PDF-upload check.

All automated checks are reproducible with pytest -q and python report/verify.py.

6.3.2 Quantitative Evaluation

Skill matching. Twelve must-have requirements were copied verbatim from the two sample postings and labelled by hand as present or absent in the sample resume. A naive exact keyword matcher, as used by simple ATS filters, was compared with the hybrid matcher (Table 6.2).

The naive matcher failed on every requirement phrased as an alternative (“LangChain or LangGraph”), a compound (“RAG and vector databases”) or with a qualifier (“Strong Python”). The hybrid matcher classified all twelve correctly, including the absent skills. This sample is small and was built from the project’s own data, so the result shows the benefit of each matching rule rather than general accuracy.

Effect of the guardrails. During development the unguarded writer produced cover letters with invented figures (“25% increase in user engagement”, “reduced response times by 30%”) and a placeholder employer (“XYZ Corporation”). With the guardrail enabled, every such draft was flagged, capped at 4/10 and returned to the writer with the problem quoted. The final selected letter contained only figures that appear in the resume.

Discussion. The results show that a small local model can drive a useful multi-agent application when its output is constrained by schemas and checked by code. The deterministic layer makes the most important outputs (which skills match, the score, and whether the letter is truthful) reproducible and explainable. The LLM contributes what it does well: reading unstructured text, judging experience and writing. Parallel execution keeps the total time to about two to three minutes on a laptop. Ollama processes requests largely sequentially on 8 GB of RAM, so the gain from parallelism is modest on this hardware but grows on machines that can serve concurrent requests.

6.4 Limitations

  1. Small-model writing quality: Llama 3.2 3B writes serviceable but plain letters, and its revisions do not always improve on the first draft. The critic’s rubric answers are noisy, which is why key checks are done in code.
  2. Occasional contradictions: the LLM’s strengths and concerns sometimes contradict the deterministic skill lists (e.g. naming a matched skill as a concern).
  3. Partial fact-checking: the guardrail verifies numbers, placeholders and gap claims, but not every qualitative statement.
  4. Extraction variance: the Job Analyst can occasionally miss or merge a requirement, which changes the score.
  5. Hand-crafted skill knowledge: aliases and skill families are a curated list and will not cover every domain.
  6. Speed: a full analysis takes about two to three minutes on an 8 GB laptop.
  7. Limited evaluation: the quantitative evaluation uses a small, self-labelled sample; a larger benchmark of real resume–job pairs with recruiter labels is needed.
  8. English text only: scanned (image) PDFs and other languages are not supported.

Chapter 7

Conclusion and Future Work

7.1 Conclusion

The project “Job Hunter: A Multi-Agent Career Copilot Using LangChain, LangGraph and Ollama” shows how agentic generative AI can be applied to a practical, everyday problem. Seven specialised agents, built as LangChain chains with Pydantic structured output and orchestrated by a LangGraph state graph, analyse a resume against a job posting, compute an explainable fit score, plan how to close skill gaps, prepare the candidate for interviews and write a cover letter that is reviewed and revised automatically.

A central lesson of the project is that reliability comes from system design, not from the model alone. Every significant failure observed with a small local model was addressed with a specific mechanism: deterministic matching and scoring, a rubric-based critic, a hallucination guardrail, output caps with fallbacks, and best-draft selection. The system runs fully offline on a student laptop, keeps personal data private, passed all 20 automated tests and all 13 test cases, and outperformed naive keyword matching on the evaluation sample.

Through this project I gained practical experience with LangChain, LangGraph, local LLM deployment with Ollama, prompt and schema design, LLM-as-judge evaluation, guardrails, and testing non-deterministic AI systems.

7.2 Future Enhancements

  1. Retrieval-augmented skill knowledge: replace the hand-written alias and family lists with embedding-based similarity over a skills taxonomy such as ESCO or O*NET.
  2. Tool-using agents: let the Gap Coach search for real courses and documentation, and let the writer fetch the company’s website for a more specific opening.
  3. Model routing: use a small fast model for extraction and a larger model for writing, chosen per agent.
  4. Human-in-the-loop: use LangGraph checkpoints and interrupts so the user can edit the extracted skills or approve the letter before revision.
  5. Resume tailoring: add an agent that rewrites resume bullet points for each posting, under the same factual guardrails.
  6. Batch mode: rank many job postings for one resume to find the best-fitting roles.
  7. Larger evaluation: build a labelled benchmark and measure matcher accuracy, score correlation with recruiter judgements, and hallucination rates across models.
  8. Observability: integrate LangSmith tracing to monitor agent latency, token usage and failures.
